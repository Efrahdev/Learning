The visual language

This manuscript has a drawing system. The same thing is always drawn the same way, in every volume, so that you can eventually draw any of it yourself, on paper, from memory. Learn these four shapes now.

Words describe. Pictures anchor. Nearly everything in this book will be shown to you as a diagram first and explained in words second, because the machine you are learning about is a physical arrangement of things — and physical arrangements are best held in the head as pictures.

Before you continue

Get a pencil and paper. Copy all four glyphs once. It will take two minutes and it will pay you back for the next thousand pages. You are not decorating — you are installing a notation.

The nine layers

When a diagram or a panel says which layer it is speaking from, it means one of these. You will constantly move up and down the list.

  1. Human problem — what a person wanted.
  2. Python — the code that asks for it.
  3. Operating system — what the kernel was asked to do.
  4. Memory — what was created, changed or thrown away.
  5. CPU — what the processor actually executed.
  6. Storage — what touched the disk.
  7. Input / output — what crossed the edge of the program.
  8. Performance — what it cost, and why.
  9. Scale — what this becomes in software used by millions.
The eight beats

Every chapter runs the same eight steps, in the same order. The rhythm never changes; only the difficulty does.

Want (a problem you can feel) → Tool (the Python for it) → Make (you write it) → Look inside (what exists now) → Break (it fails) → Descend (the machine explains why) → Rebuild (a better model) → Anchor (the picture you keep).

Beat 5 matters most. The machine explanation is never volunteered. It always arrives as the answer to something that just went wrong in front of you. That is what makes it stick instead of washing over you.

The one discipline

Predict, run, reconcile. Before executing anything in this book, write down what you think will happen. Then run it. Then explain the difference. The gap between your prediction and reality is the only place learning happens — reading correct code teaches almost nothing, because nothing surprises you.

The conversation

Your first Python. Also your first proof that the answer arriving on screen took a journey of about two million steps — and that two separate machines were running to make it happen.

Beat 1

Want

A problem you can feel before any solution is offered.

Right now, inside your computer, a processor is executing something like three billion instructions every second. Not one of them is yours.

It is running the operating system, the window you are reading this in, a dozen background programs. It is enormously busy and completely uninterested in you. You know it can fetch an instruction, decode it and execute it. You have never once told it which instruction.

So: how do you get in? Not “how do you learn programming” — how do you physically insert an instruction of your own into a machine that is already full of somebody else's?

Beat 2

Tool

The Python for it, explained from nothing.

There is a door, and it has been there since the 1960s. It is called a prompt: a place where the machine stops and waits for you specifically.

Open a terminal — the plain window where you type commands rather than click things. On a Mac it is called Terminal; on Windows, PowerShell or Windows Terminal; on Linux, Console or Terminal. Type this and press Enter:

Those three arrows are the door. They mean: I have stopped. I am waiting. Your turn.

Where the prompt came from

It is older than Python and it was fought for. Into the early 1960s, using a computer meant punching your program onto stiff paper cards, handing the stack to an operator, and going away. Hours later — often the next day — you collected a printout. One mistyped character cost you a day.

Researchers argued that this was intolerable, and built machines that many people shared at once, each getting slices of the processor's attention, each able to type something and get an answer now. It was called time-sharing, and it changed what a computer was for: from a calculating engine you fed, into something you could hold a conversation with.

Your >>> is that argument, won.

Beat 3

Make

You write it. Nothing is assumed.

Arithmetic: the machine already knows this much

Type 2 + 2 and press Enter.

Four things to notice, and each is a real fact rather than a detail.

  • * means multiply, not ×. There is no multiplication sign on a keyboard, so early languages borrowed the asterisk and everybody has used it since.
  • / means divide. Likewise: no ÷ key.
  • You did not have to ask for the answer. You typed something and the answer appeared. Remember this — Beat 5 shows it stops being true the moment you write a program in a file.
  • 20 / 4 gave 5.0, not 5. That trailing .0 is not decoration. It is a different kind of number, and Chapter 2 is largely about why.

Spaces around the + are optional. 2+2 works identically. Python ignores spaces here; humans do not, so put them in.

Your first function: print

Arithmetic is the machine showing off. Now make it do something because you said so.

Small line, four new ideas. Take them one at a time.

1. print is a function. A function is a named job that already exists. Somebody wrote it long ago; you are asking for it by name. Python arrives knowing roughly seventy of these.

2. The round brackets mean “do it now.” They are called parentheses. Writing print alone names the job without asking for it. Writing print() asks for it. That distinction seems fussy today and becomes one of the most important facts in the language around Chapter 8.

3. What sits inside the brackets is the argument — the thing you are handing over. print takes what you give it and shows it.

4. The quote marks make text. Anything between quotes is a piece of text, called a string — letters strung together. Quotes are how you tell Python “these characters are data, not instructions.”

Notes to yourself

A # tells Python to ignore the rest of the line. Everything after it is for humans.

Leaving, and coming back

Type exit() — with the brackets, because it is a job and you want it done — or hold Ctrl and press D. Everything you typed disappears. The prompt keeps nothing. That is not a flaw; it is what a conversation is, and Beat 6 explains what the machine does with the words instead of saving them.

Do this now

Before reading on, spend five minutes at the prompt. Multiply large numbers. Print your name. Print a sentence with a full stop in it. Try print(2 + 2) and then print("2 + 2") and work out why they differ. You are building a physical habit; reading about it is not the same thing.

Beat 4

Look inside

What actually happened while you were typing.

You pressed one key and a letter appeared. That felt instant. It was not — it was a relay race with about nine handoffs, and your Python was asleep for most of it.

Two things in that chain deserve to be pulled out and stared at.

The terminal drew your letters, not Python. You can prove it. Start a Python program that just waits, then type into the window — your letters still appear, even though nothing is reading them. The echo is the terminal's doing, entirely separate from the program.

Your program is not allowed to touch the screen. Nothing you write ever will. Programs run in a restricted mode where the hardware itself refuses them access to devices. To show something, a program must ask the kernel — a formal request called a system call — and wait.

Beat 5

Break

Make it fail on purpose. This is where the real learning starts.

Type a bare word — no quotes, no brackets.

Nothing is broken. The machine is talking to you, precisely, and this is a skill to build immediately rather than a wall to fear.

“Name error. The name hello is not defined.” In your own words: “I used a word Python has never met.” With quotes it becomes text and works fine — print("hello"). Without them, Python reasonably assumes you are naming something, and you have not named anything yet. Chapter 3 is where you start.

A second kind of failure

Different shape, different meaning. A SyntaxError means Python could not even work out what you were trying to say — it never got as far as attempting it. A NameError means it understood you perfectly and could not carry the instruction out. Understanding-failure versus doing-failure. That distinction will save you hours.

Break it deliberately

Get all four of these, and say each one out loud before reading the next:

print("hi" — a missing bracket · print(hi") — a missing quote · Print("hi") — a capital P · print("hi") extra — trailing rubbish. Predict which give SyntaxError and which give NameError before you run them.

A running program does no such thing — it computes 2 + 2, gets 4, and throws it away, because you never asked for it to be shown.

That is why print exists. In a real program, nothing appears unless you say so.

Beat 6

Descend

Now the machine explains itself.

Between you pressing Enter and the answer appearing, Python did something almost nobody is told about: it translated your text into a different language first. It does this every time, for every line.

You can see the real tape. Python will show you its own instructions:

Seven steps to print two letters. POP_TOP is throwing away the answer print handed back, because you did not want it. Nothing here is hidden from you — it is simply never visited.

Not a promise

These instruction names are not part of Python. They belong to one particular program that runs Python, and its authors change them in nearly every release. Keep this distinction sharp for the rest of your life: the language is the set of promises; the program that keeps them is something else. Confusing the two is the commonest source of confidently-wrong statements about any language.

The fact this chapter exists for

Now hold two things together. You know the processor works in a cycle: fetch an instruction, decode it, execute it, repeat. And you have just seen that Python reads a tape of instructions one at a time and carries each one out.

Those are the same cycle. Happening twice. One inside the other.

The central idea of Volume I

There are two fetch–decode–execute loops running, one inside the other.

The outer one is made of silicon. It is a physical object and it does not know Python exists.

The inner one is a program running on that hardware. It reads your instruction tape and carries out each step — and each of its steps takes the outer machine dozens or hundreds of real instructions to perform.

Python is a machine pretending to be hardware, running on hardware.

Layer 5 · CPU · what that costs

Adding two numbers is one instruction for the outer ring — about one cycle. Adding two numbers in Python takes perhaps a hundred: fetch the tape step, decode it, find the two values, look up what kind of things they are, find the right adding routine, run it, build a place for the answer, put the answer there.

Roughly a hundredfold. Not because Python is badly built — because it is doing a hundred times more work, in exchange for never making you say in advance what kind of thing anything is. That trade is the subject of the next chapter.

Layer 6 · Storage · where the tape is kept

Translating your text costs real time. Doing it every run of a program you use often would be wasteful — so Python saves the finished tape to disk, in a folder named __pycache__, and reuses it. It also records the source file's size and the time it was last changed. On the next run it compares. If you edited the file, the saved tape is thrown away and a new one made.

This is the shape of every cache anywhere in computing: keep the expensive answer, plus enough information to know when it has gone stale. Notice what is not saved — anything you type at the prompt. No file appears. You are never going to run that exact line again.

Beat 7

Rebuild

The better model, now earned.

The prompt has a name that says exactly what it does: a REPL — Read, Evaluate, Print, Loop. Four steps, forever, until you leave. Every mystery in this chapter is one of those four.

Become the machine

I am the Python program, and a line has just arrived. I split it into pieces. I work out which piece depends on which. I write a short tape of tiny steps. Then I begin: read step one, work out what it means, do it. Read step two, work out what it means, do it. I have no idea what any of it is for. I never wonder. I just take the next step, forever, until the tape runs out — and then I print whatever value is left over and go back to waiting.

Misconception

“Python is interpreted, so it doesn't compile.”

You watched it compile. Every line becomes a tape before anything runs. What is true is that the tape is not made of instructions your processor understands — it is made for the inner ring, which then acts them out on the outer one. That extra layer is the whole story, and it is a very different statement from “it doesn't compile.”

Misconception

“The terminal is Python.”

Two separate programs with separate memory, connected by a channel the kernel manages. The terminal drew everything you typed. Python saw none of it until you pressed Enter.

Beat 8

Anchor

What you keep.

Reflection

The interrupt in Figure 1.2 forced the processor to abandon whatever it was doing and run the operating system's code instead. Your keystroke genuinely interrupted something mid-sentence.

So: what happens if two devices interrupt at the same instant? And what stops a badly-behaved device from interrupting so often that nothing else ever gets to run?

Mental model — Chapter 1
  • >>> means your turn. It is a conversation, won as an argument in the 1960s.
  • print(...) — a name, then brackets meaning “do it now”, then the argument. Quotes make text.
  • A keystroke is a relay race of nine handoffs. Your program is asleep for most of it and never touches hardware.
  • Read errors bottom line first. Say it aloud, then say what it means. SyntaxError = couldn't understand you. NameError = understood, couldn't do it.

Making values

Every kind of thing Python can hold, and how to make each one. Then the discovery that they are all the same shape underneath — and that the four extra bytes of paperwork on a number explain almost everything about the language.

Beat 1

Want

A problem you can feel.

In Chapter 1 you could add numbers and print words. That is almost nothing. A program that mattered would need prices with pennies in them, names, yes-or-no answers, and numbers far bigger than a calculator holds.

And there is a harder question sitting underneath. You typed 2 + 2 and also print("hello"). One is a number, one is text. But memory holds only numbers — you know this. Every byte is a value from 0 to 255. So how does the machine tell text from a number at all?

Keep that question. Beat 6 answers it exactly, and the answer is the foundation of everything else in this book.

Beat 2

Tool

The Python, from nothing.

Two kinds of number

Python has whole numbers and numbers with a decimal point, and it treats them as genuinely different kinds of thing.

A whole number is called an int, short for integer. One with a point is a float — a strange name that comes from “floating point,” meaning the decimal point can move about to suit the size of the number. 7 and 7.0 are equal in value and different in kind, exactly as a photograph of a chair and a chair are both “a chair” and not the same thing.

No commas in numbers. 1,000 is not one thousand to Python — it is two separate numbers. Write 1000. If you want it readable, underscores are allowed: 1_000_000.

The full set of arithmetic

The last three are new and all three earn their place.

// is floor division. It answers “how many whole ones fit?” Thirty children, four to a car: 30 // 4 is 7 full cars.

% is the remainder, usually said as “mod.” 30 % 4 is 2 children left over. This operator is far more useful than it looks — it is how you tell whether a number is even (n % 2 is 0), how you wrap a clock round from 23 back to 0, and how you take every third item from a list.

** is power. Two stars, not the ^ you may have seen elsewhere — ^ means something entirely different in Python.

Do this now

Work out how many hours and minutes are in 500 minutes, using only // and %. Then check: does your answer come to 500 again when you multiply back? Then try 2 ** 1000 and look at what comes back — Beat 5 explains why that did not break anything.

Text

A piece of text is a string. Quotes make one — single or double, they behave identically.

Both kinds exist so that you can put one inside the other. A sentence with an apostrophe needs double quotes around it; a sentence quoting speech needs single. Python shows strings back to you with single quotes by default, unless there is an apostrophe inside, in which case it switches. That is a display habit, not a difference in the string.

Strings can be joined and repeated:

len is a second built-in job, like print. It answers “how many pieces?” Note that joining requires you to supply the space yourself — Python adds nothing you did not ask for.

Yes and no

There is a kind with exactly two values, spelled with capital letters: True and False. They are called booleans, after George Boole, who worked out the mathematics of true-and-false a century before there were computers to run it on. You get them by asking comparison questions:

Two equals signs asks a question. One equals sign does something quite different, which is Chapter 3's subject. != means “is not equal to.” These become the engine of Chapter 4, where your programs start making decisions.

Turning one kind into another

These are jobs whose names are the kind you want. int(7.9) giving 7 rather than 8 is deliberate: int promises to remove the fractional part, not to round. If you want rounding, ask for round(7.9).

Asking the person at the keyboard

input shows your prompt, waits for a whole line, and hands back what was typed. Look closely at what came back: 'Ada', with quotes. input always gives you a string. Always — even if the person typed digits. That single fact causes almost everybody's first serious bug, and you will meet it in Beat 5.

Beat 4

Look inside

What exists in the machine now.

Python will tell you what kind any value is, and it costs nothing to ask.

Now ask something stranger. How much room does the number 7 take up?

Twenty-eight bytes. For the number seven.

You know that seven fits in a single byte — it is 00000111. Twenty-eight is preposterous. Twenty-seven of those bytes are not the number.

So they must be something else. Here is what a value actually looks like in memory, and this glyph will not change for the rest of the manuscript.

And the crucial part: everything wears the same shape. Only the band and the payload change.

Layer 4 · Memory · where these live

Not in your program's instructions, and not on the stack. They live on the heap — the large open region a program asks the operating system for when it needs storage that outlasts the moment. Every value you can name in Python is out there.

You can see the address. In the usual Python, id(7) hands you the actual location in your computer's memory. Try hex(id(7)) to see it in the form you would recognise from a memory dump. You are being handed a real place.

Beat 5

Break

Four failures. Each opens a door.

Break 1 — the same plus sign, two meanings, then a wall

Read the first two again. Identical operator. Completely different answers. With numbers, plus means make bigger. With text, plus means join on the end. And then the third stops dead.

Say the error aloud: “Type error. Can only concatenate str, not int, to str.” Concatenate means join. In your own words: “I can only join text to text, and you gave me a number.”

Break 2 — the bug everybody writes once

You typed a number. You got text. input hands back a string no matter what, because it cannot know what you meant — the person might have typed a name, a date, or nonsense. Deciding is your job: int(input("Age? ")). This is exactly why shop.py in Beat 3 had that conversion line.

Break 3 — division that changes kind

Two whole numbers went in and a float came out. Python does this on purpose. Division is the one operation that usually does not give a whole number, so rather than sometimes returning one kind and sometimes another — which would make every program unpredictable — it always returns a float. Consistency was chosen over convenience, and when you genuinely want the whole-number answer, // is right there.

Break 4 — arithmetic that gets it wrong

That is not a typo and not a mistake. It is the most famous surprise in computing, and Beat 6 explains it in three sentences using something you already know.

Beat 6

Descend

The machine answers all four.

Why the label exists at all

Return to the question from Beat 1. Memory holds numbers. So how does the machine know text from a number?

It cannot, from the bytes. Eight bits could be anything. Meaning has to be recorded, and there are only two places to record it: in the program, or in the data.

Some languages put it in the program. You state in advance that a thing is a whole number; the translator uses that to pick the right machine instruction; the knowledge is baked in and thrown away. Fast, and you must declare everything.

Python puts it in the data. Every value carries its own label. Nothing has to be declared, because anything can always be asked.

First principle

Twenty-four bytes of paperwork is the price of never having to say what kind of thing something is.

Nothing was given to you free. The cost moved from your fingers into your memory.

What + actually does

Now Break 1 becomes obvious. The plus sign does not mean add. It never did.

The rule behind Break 1

+ does not mean add. + asks the thing on the left what it wants + to mean.

Numbers answer: adding means making bigger. Strings answer: adding means joining. In Volume II you will write your own kinds of thing, and you will answer that question yourself.

And now Break 1's third line explains itself:

Become the machine

I have been asked for 5 + 3. I take the two addresses off my stack. I follow the first one to its object and read its kind pointer. I follow that to the object describing int, and look inside for the entry marked “how to add.” I find a routine. I run it, handing over both addresses. It checks both really are ints. It adds their digits. Now it needs somewhere to put the answer — the answer is a new thing — so I find free space on the heap, write a count of 1, write the int kind pointer, write the size, write the digit 8, and hand back that address.

One plus sign. All of that. Now you know where the hundredfold from Figure 1.6 goes.

Why 0.1 + 0.2 misses

You know binary. That is all this needs.

Write one third in decimal and you get 0.3333… forever. It is not a flaw in you or in decimal — one third simply has no exact finite form in base ten. You round, and the rounding shows up in any sum you do with it.

A float is stored in binary, in a fixed 64 bits. And 0.1 has no exact finite form in binary — it repeats, exactly as a third does in decimal. So the machine stores the closest value that fits, which is very slightly off. Same for 0.2. Add two slightly-off numbers and the error becomes just large enough to appear.

That is what is really in memory when you write 0.1. Every language using this format behaves identically, because it is the hardware's format rather than Python's. It is why money is never stored as a float — shop.py counted whole pence for exactly this reason, and now you know it was not an arbitrary choice.

Why big numbers never break

Look again at the third field in Figure 2.3: how many digits. A Python integer is not a fixed box of 32 or 64 bits. It is a variable-length list of digit chunks, and the object simply grows.

The only limit is your memory. This costs speed on every single arithmetic operation — the routine must check the length rather than issuing one instruction — and buys you a guarantee that a number will never silently wrap round to something absurd.

Layer 8 · Performance · the second reason Python is slow

Chapter 1 gave you one reason: the inner ring. Here is the second, and for number-crunching it is usually the larger of the two.

Every value is a separate object, sitting wherever the heap had room. Reading one means following an address to a place the processor cannot predict. You know the cache pulls in a 64-byte line at a time and that a main-memory fetch costs hundreds of cycles. Scattered 28-byte objects defeat the cache completely — the processor spends most of its time waiting rather than calculating.

This is the exact reason libraries like NumPy exist. They store raw numbers side by side with no headers at all, giving up flexibility to win the cache back. Volume II builds that from the ground up.

Layer 6 · Storage · none of this reaches disk

The header, the address, the digit array — all of it is a memory-only arrangement. The moment a value is saved to a file it must be flattened into plain bytes, and every trace of the object shape is discarded. Reading it back builds a brand-new object with a brand-new address. Volume III is about that crossing, and how much information is lost each way.

Beat 7

Rebuild

The model you now hold.

There are no numbers and no words in your computer. There are only labelled things on the heap, all the same shape, and every operation begins by reading the label.

Misconception

“7 and 7.0 are the same number written two ways.”

They are equal in value and different in kind. Different band, different payload, different adding routine, different memory size. 7 == 7.0 is True because int's comparison routine is deliberately written to cope with floats. That is a courtesy someone coded, not a fact about the universe.

Misconception

“Python is slow because it is interpreted.”

The single most useful line of Python, and the single most damaging picture ever drawn of it. There is no box. There has never been a box. What there is instead explains sharing, deleting, scope and half the surprises in the language.

A problem you can feel.

Where the symbol came from

The original notation for this was an arrow: age ← 10. That is exactly right, and it says exactly what happens — put this label on that thing. Nobody would ever have confused it with mathematical equality.

Then keyboards arrived, and keyboards had no arrow key. = was already there, so = was borrowed. That one act of convenience created a confusion that has been taught, mis-taught and untaught for sixty years, and forced the invention of == to mean the thing = used to mean.

The two boards, and why del print healed it

Python does not have one board. At this stage of your learning it has two, and it searches them in a fixed order.

So del print did not repair anything. It removed the row you had put in the way, and the search fell through to the board behind it — where the real print had been sitting unharmed the whole time.

What this tells you about Python

Nothing is protected by magic. Things are protected only by nobody choosing to overwrite them.

That is a real design decision with a real cost. Python trusts you completely, and the price of trust is that you can break your own interpreter in one line. Later this same openness is what lets test frameworks find your tests and debuggers show you your variables — the boards are readable and writable, so tools can use them.

Become the machine

I have reached LOAD_NAME with the text “print”. I take the six characters and run them through a hashing calculation to turn them into a number. I use that number to jump straight to a slot in your board's table. Something is there — I compare the stored text with mine, character by character, to be sure it is not a coincidence. It does not match, or the slot is empty. Your board does not have it.

So I do the whole thing again on the built-in board. Hash, jump, compare. Found. I read the eight bytes stored there — an address — and push it onto my stack. Now, finally, I can move on to the next instruction.

Layer 5 · CPU · what a name costs

Every single use of every single name does that. Hash the text, jump to a slot, compare, possibly try a second slot, possibly search a second board, then read an address. That is dozens of machine instructions and several memory accesses that may not be in cache.

Compare it with the alternative: if the machine could know in advance that x was always slot 3, reading it would be one addition and one memory read. It cannot know that here, because you might add a row to the board at any moment — including from another part of the program entirely.

This is the cost of the openness described above, and it is paid on every line. Chapter 8 shows you where Python claws most of it back, and the trick will make sense only because you understand what is being avoided.

Layer 4 · Memory · the board is itself an object

globals() handed you something you could index with square brackets. That is not a coincidence — the board is an ordinary Python object living on the heap, with a header exactly like everything else in Figure 2.1. Volume II takes it apart completely and shows you how the hashing works.

So when a program runs, memory contains: your objects, plus a board object holding their addresses, plus a second board object holding the addresses of everything built in. Names are not free. They are data.

Layer 6 · Storage · none of this survives

Close Python and the board is gone. Every row, every object, every address. The heap is handed back to the operating system and reused by something else within milliseconds.

Names hold things for the lifetime of a running program and not one instant longer. If you want something to outlive the program, it has to be written to a file — bytes on a disk, with every trace of the board structure flattened away. That crossing is the whole of Volume III, and now you know precisely what is being lost at it.

What del actually does

Given the board, del becomes obvious and much narrower than its name suggests. It removes a row. It does not delete an object.

The object had two arrows; now it has one. Nothing was destroyed. The count in the header simply dropped from 2 to 1.

What a decision is

Look at the tape. Chapter 1 told you your text becomes a list of tiny steps that the read-head works through one at a time. Everything you have written so far ran straight down that list. Not any more.

There is no if instruction. There is no block. There is one instruction whose whole job is to move the read-head somewhere else if the answer was false.

The central idea of Chapter 4

A decision is a jump. Indentation is how you draw the jump on paper.

Your spaces never reach the running machine. The compiler reads them, works out how far each leap has to travel, writes that distance into a jump instruction, and discards the whitespace entirely. By the time your program runs there is no indentation anywhere — only numbers saying how far to move the read-head.

That is also the honest answer to why Python is fussy about spaces. Other designs use brackets to mark a block and let the spacing be decorative — which means the spacing can lie, showing you one structure while the brackets say another. Python removed the possibility by making the thing you see be the thing that runs. It costs you some discipline and buys you the guarantee that a program always means what it looks like.

Why and and or are also jumps

(You have not met def yet — that is Chapter 8. Copy it for now; it simply makes a job that announces itself.)

Once the answer is settled, the rest is skipped. If the left side of an and is false, nothing on the right could rescue it, so Python jumps past it without evaluating it at all. This is called short-circuiting, and it is not an optimisation you can ignore — it changes what your program does.

The two questions, and why they disagreed

Break 7 needs two facts, and you have already met one of them.

Fact one: is and == are not variations of the same question.

Fact two: there is a cupboard of pre-built numbers.

Chapter 2 left you worried. Every arithmetic operation builds a brand-new object, and programs add small numbers constantly — a loop counting to a million would create and destroy a million objects. That would be unaffordable.

So Python does not do it. Before your program starts, the interpreter builds every integer from −5 to 256 and keeps them on a shelf. Whenever a number in that range is needed, no object is made; the address of the existing one is handed over.

This is also why sys.getrefcount(5) gave you thousands back in Chapter 3. There is only one 5 in the entire running system, and everything that needs a five points at it.

Why the shelf is allowed to exist

A thing that can never change is safe to share with everybody.

Suppose you could reach through a and alter the object 5 into a 6. Every five in the entire program would become a six, including in code you never wrote. It would be a catastrophe.

It cannot happen. There is no operation anywhere in Python that modifies an existing number — a = a + 1 builds a new object and moves the arrow, exactly as Figure 3.4 showed. Because numbers cannot change, sharing them is free of risk, and the shelf becomes possible. The restriction is what buys the optimisation. Chapter 7 is about what happens with things that can change.

Not a promise

−5 to 256 is a decision by one particular interpreter, not part of Python. Never write code whose correctness depends on it. Use it to explain behaviour you observe, and use == when you mean equality. Code that works because a is b happened to be true for small numbers will fail the day someone passes it 300.

Layer 5 · CPU · the hidden cost of a decision

A jump is not free, and the reason connects directly to something you already know about processors.

A modern CPU does not finish one instruction before starting the next. It has a pipeline — perhaps fifteen or twenty stages deep — with many instructions in flight at once, at different stages of completion. That is how it reaches billions per second.

A jump wrecks that, because the processor does not yet know which instruction comes next. So it guesses. It keeps a record of which way each branch went last time and bets on the same again. Guess right and the pipeline never stalls. Guess wrong and everything speculatively started must be thrown away and refetched — typically fifteen to twenty cycles lost, which is an eternity.

Real predictors are right well over ninety per cent of the time, because real branches are lopsided: the error case almost never happens, the loop almost always continues. Predictable decisions are nearly free; unpredictable ones are expensive. Nothing you can write in Python controls this directly — but it is running underneath every if in your program, and in Volume II it becomes something you can measure.

First principle

A for loop is a conversation. Python asks an object “what comes next?” until the object says “nothing.”

It never counts. It never knows how many there will be. It simply keeps asking, and stops when it is told to.

You can hold that conversation yourself, one line at a time. Two new built-in jobs: iter asks an object for a fresh counter-keeper, and next asks that keeper for one item.

The jump, pointed backwards

Chapter 4's reflection asked what would happen if a jump sent the read-head backwards. Here is the answer, on the tape.

The central idea of Chapter 5

A loop is a jump backwards. That is the entire mechanism.

The read-head is simply told to move to an earlier position on the tape, and carries on from there as though nothing unusual had happened. It has no concept of repeating, no memory of having been there before, and no idea it is in a loop at all.

And now Break 1 is not mysterious at all. The read-head goes round, reaches the test, and the test asks about an object nothing has changed. Of course the answer is the same. The machine is not stuck — it is being perfectly obedient.

break and continue are just two more jumps

What for compiles to

Compare it with the while tape above. Identical shape — one forward jump, one backward jump. The only difference is what the test is. A while tests a condition you wrote. A for asks an object a question.

And Break 4 is now completely explained. Look at the order: FOR_ITER gets the next value, and then STORE_NAME writes it into i. Setting i yourself changes a row on the board that the very next turn will overwrite anyway. The counter-keeper never looked.

Become the machine

I have reached FOR_ITER. I take the counter-keeper from my stack. I call its “what's next” routine. It has its own private position stored inside it — it adds one, checks whether it has passed the stop value, and hands me back an object. I push that object onto the stack and step forward, where STORE_NAME will file it under i.

Next time round, the keeper's position has moved on. Eventually it tells me there is nothing left. Then, and only then, do I jump out. I never counted anything. I asked, every single time.

Layer 5 · CPU · why loops suit hardware perfectly

Two things you already know come together here, and both work in a loop's favour.

Branch prediction. Chapter 4 explained that the processor guesses which way a jump will go, and pays fifteen to twenty cycles when it guesses wrong. A loop running a thousand times takes the backward jump 999 times and skips it once. That is the most predictable branch in all of computing — the predictor gets it right essentially always, and pays the penalty once, on the way out.

The instruction cache. A loop body is a small handful of instructions executed over and over. After the first turn they are sitting in the fastest cache the processor has, a few cycles away. The machine is never fetching new instructions from main memory. It is the ideal workload for the hardware — which is why the tightest loops in the world are written to fit inside that cache deliberately.

So the outer ring of Figure 1.6 is delighted by loops. The inner ring is another matter: every turn still costs the interpreter its full fetch-decode-execute overhead for each bytecode. A million-turn Python loop is roughly a hundred million machine instructions. The hardware is doing beautifully; there is simply a great deal of it to do.

One oddity, mentioned for completeness

Python lets you attach else to a loop. It runs only if the loop finished without hitting break — useful for “I searched everything and found nothing.” It is also read wrongly by almost everybody, because else suggests “otherwise” rather than “no break happened.” Many experienced programmers avoid it. Know that it exists; think twice before using it.

What is a list in memory?

Chapter 5's reflection asked you to sketch this. The requirements were: hold many objects, keep them in order, reach any one quickly, and be able to grow.

Memory is one enormous numbered row of bytes. The obvious plan is to lay the items side by side, because then reaching item n is pure arithmetic rather than a search.

A list is a row of addresses. Your things are not in the row — only directions to them.

Every single index you write is checked against the number of items in use before the arithmetic is allowed. That is a comparison and a branch on every access — a small tax, paid billions of times.

What it buys is that pets[3] can only ever produce a clear error. Without the check, the arithmetic would happily compute an address just past the end of the row and read whatever eight bytes happened to live there — another program's data, or nonsense, treated as though it were a valid address. Reading a made-up address is how a great many serious security failures have worked. Python pays the tax so that this can never happen to you.

Why this arrangement works

Most appends are free. The rare expensive one is paid for by the many cheap ones before it.

Suppose the row grew by exactly one slot each time. Building a list of a million items would copy 1 + 2 + 3 + … + 1,000,000 addresses — half a trillion copies. Unusable.

Because the spare capacity grows in proportion to the list, the number of expensive appends stays a small fraction of the total, and the whole job of building a list of n items costs an amount proportional to n. The cost is uneven, and the total is fine.

Why pop(0) is ruinous

Become the machine

I have been asked to insert(0, x) on a list of a million items. There is a spare slot, so I need no new block. But slot 0 is occupied and everything must move up.

I start at the end so as not to overwrite anything. I copy slot 999,999 into slot 1,000,000. Then 999,998 into 999,999. Then 999,997 into 999,998. I do this a million times — eight megabytes read, eight megabytes written, every cache line in the row thrown out and refetched. Only then can I write one address into slot 0.

One insert. Sixteen megabytes of traffic. And the code that caused it was three characters longer than append.

This is the characteristic shape of a performance bug: correct, readable, passes every test you write with ten items, and unusable at a hundred thousand. A queue written with pop(0) inside a loop is the commonest example in all of Python.

What a slice really builds

The row is tidy; what it points at is not

Layer 5 · CPU · putting numbers on it

You know the cache fetches a whole line at a time — sixty-four bytes. Eight addresses fit in one line, and they are read in order, so the processor spots the pattern and fetches the next line before it is asked. That part costs almost nothing.

Then each address must be followed to a 28-byte object sitting somewhere unpredictable. The processor cannot fetch ahead, because it does not know where to go until it has read the address. If that object is not already in cache, it stalls for two to three hundred cycles — long enough to have done hundreds of additions instead.

Summing a list of a million numbers can therefore issue a million potentially-stalling reads. That, more than the inner ring of Figure 1.6, is why numeric work on lists is slow — and it is exactly the problem Volume II solves by storing numbers side by side with no headers and no scattering at all.

Why sharing is the correct default

The obvious complaint is that Python should simply copy on assignment and spare everyone the trouble. Work out what that would cost.

The central idea of Chapter 7

Aliasing is free. Mutation is broadcast. Danger lives exactly where they meet.

Two names on an unchangeable thing — a number, a word, a tuple — is perfectly safe, and is precisely why Chapter 4's shelf of small integers is allowed to exist.

Two names on a changeable thing means a modification made through either is instantly visible through the other, and through every other reference anywhere in the program.

Analogy

A photocopy and a shared whiteboard. Photocopy my notes and hand you the copy: we each scribble freely and neither affects the other. Instead tell you which room the whiteboard is in, and we are both looking at one surface — when I rub something out it vanishes from your view too, without warning, possibly mid-sentence.

b = a is telling someone the room number. It is not, and can never be, a photocopy.

Two instructions, not one

The tape settles the rebinding-versus-mutating question completely. These are not two flavours of assignment — they are different instructions doing different jobs in different places.

One touches your name board. The other touches the heap. They share a symbol and nothing else.

How deepcopy survives a list that contains itself

It keeps a notebook. Every object it copies is recorded — the original's address on the left, the new copy on the right. Before copying anything it checks the notebook first.

The kernel solves this problem better than Python does

Layer 3 · Operating system · copy-on-write

The operating system faces exactly this dilemma constantly, and its answer is more elegant than anything available inside Python.

When one program starts a copy of itself, the child appears to receive a complete duplicate of the parent's memory — possibly gigabytes. Copying that would be absurd, so the kernel does not. It points both programs at the same physical memory pages and marks them read-only.

Both read happily from shared memory, at full speed, with nothing duplicated. The instant either one writes, the hardware raises a fault, the kernel quietly copies just that single four-kilobyte page, and lets the write proceed into the private copy.

Share until somebody changes something, then copy only the part they touched. It is the perfect answer to this chapter, implemented in silicon. Python cannot do it for individual objects — it has no way to be notified that you are about to modify a list — but knowing the ideal exists tells you the shape of what you are working around. Volume III returns to this properly.

Become the machine

I have been given backup = scores. I look up “scores” on the board and read eight bytes: an address. I write those same eight bytes into a row called “backup.” I add one to the count in that object's header.

I never looked at the list. I do not know how long it is. I do not know what is in it. It could hold three things or three million and my work would be identical. Nobody asked me to make a copy and I did not make one — I was told to write down an address, and I wrote down an address.

Why this matters beyond Python

This difficulty is as old as stored-program computing. Programmers hit it in the 1950s: two registers holding one address, one routine modifying what another was reading. It has never been solved so much as repeatedly managed.

Tony Hoare, who introduced the null reference in 1965, later called it his “billion-dollar mistake” — an admission that handing programmers unrestricted references was a decision whose consequences were measured in decades of crashes.

Some modern languages take the most radical position available: the compiler tracks every reference and simply refuses to build a program in which one part could modify data another part is reading. Whole languages have been designed around the contents of this chapter. That is the measure of how serious it is.

[] gives me a new empty list at 0x5500. I store that address in the object's defaults field, build the object, and write one row on the board.

Much later someone calls without that argument. I do the only thing available to me: copy 0x5500 into the frame slot. Nobody ever gave me a recipe for making a list. They gave me a list.

Note is None rather than == None — Chapter 4's distinction, used correctly. There is exactly one None object, so identity is precisely the right question.

The rule to carry forever

Never use a list, a dictionary, or anything else changeable as a default value. Numbers, strings, True, False, None and tuples are all safe, for exactly the reason Chapter 7 gave: a thing that cannot change is safe to share.

Why recursion stops

Every recursive function needs both halves: a case that stops, and a step that moves towards it. Miss either and you get Figure 8.6's lower half.

Layer 5 · CPU · what a call costs

Calling a function is not free. A frame must be built, argument addresses copied in, a return position recorded, and on the way out the frame released and every count decremented. That is real work — commonly a few hundred machine instructions in Python, far more than the handful an if costs.

The consolation is that everything inside the function then runs on numbered slots instead of hash lookups, which is meaningfully faster than the same code at module level. A function that does a decent amount of work more than repays its own call cost. One called a million times to do almost nothing does not.

Never let that stop you writing functions. The cost of a program you cannot understand is always larger.

The machine explains all six.

The problem nobody can avoid

A byte holds a number from 0 to 255. That is all a byte does. To store the letter A, somebody must first decide which number means A. There is no correct answer — only a convention. And conventions can conflict.

First principle

Bytes have no meaning. An encoding is a claim about what somebody meant.

There is no way to look at bytes and know for certain what text they represent. Programs guess — from a file extension, a header, a setting — and when they guess wrong you get Break 5.

The fix: split one problem into two

ord and chr from Beat 2 are simply you reading the top box directly. ord("🐍") is 128013 because that is the number the registry assigned it.

UTF-8, and why it won

The obvious encoding gives every character four bytes. It works, and it wastes three-quarters of every English document.

In September 1992, two engineers designed the alternative over dinner in a New Jersey diner, sketching it on a placemat. It uses one byte for common characters and up to four for rare ones — and the bit patterns are chosen with great care.

Two kinds of thing, and the boundary between them

Python keeps text and data strictly apart, and Break 5 is what the boundary looks like when you cross it carelessly.

Why one emoji made the whole string heavier

Python promises that len counts characters and that word[500] is instant. Instant means arithmetic, and arithmetic — Figure 6.4 — needs every slot to be the same width.

So Python does not store strings as UTF-8 internally. It looks at the widest character present and picks one width for the entire string.

And Break 4 dissolves. len("🐍") is 1 because it is one entry in the registry. Its UTF-8 form is 4 bytes because that is how you write the number 128013 down. Two correct answers to two different questions.

Why join exists

An honest note

The interpreter has a special trick that sometimes makes s = s + "x" avoid the full rebuild. It is fragile, undocumented as a guarantee, and disappears the moment a second name points at the string. Do not build a habit on it. Collect in a list and join.

Become the machine

I have been asked for "caf" + "é". I look at both strings. The first uses one byte per character; the second needs more, so the answer must too. I work out the total length: four characters. I ask for a new block of memory the right size, write a header saying str, length 4, two bytes each, and copy all four numbers in — widening the first three as I go.

I did not extend anything. I could not. Both originals are exactly as they were, and there is now a third string that neither of them knows about.

Layer 6 · Storage · none of this reaches disk

The one-, two- or four-byte layout is a memory-only arrangement. Files and networks carry encoded bytes and nothing else — no header, no width, no length. When you open a file in text mode, Python quietly picks an encoding for you, and on some systems that default is still not UTF-8.

Pass encoding="utf-8" explicitly. Always. It is the difference between a program that works on your machine and a program that works. Volume III follows the whole path from open() down to the disk block.

The machine explains all six.

What raise actually does

Two steps, and the second is the interesting one.

Build. An object is created on the heap — header, kind, message — exactly like every other object you have made.

Unwind. Python abandons the current frame and hands the object to the frame below. If that frame has no handler, it abandons that one too. It keeps going down the stack from Figure 8.3 until either a matching except is found or there are no frames left.

The central idea of Chapter 11

An error is a thing, thrown downwards through the frames, until somebody catches it.

If nobody does, it reaches the bottom, the program stops, and the list of frames it passed through is printed for you. A traceback is not a punishment. It is a map of exactly where the object travelled.

Which is why the phrase says most recent call last. The frame where the trouble actually happened is at the bottom of the printout, because that is the order the frames were passed. Read tracebacks from the bottom up — the last line names the kind, and the line above it names the place.

Become the machine

I have hit a raise. I build the object. Then I stop running this frame's tape and look for an active try that covers the instruction I was on. There is none.

So I record this frame in the object's travel notes, release every slot in it, drop every count by one, and hand the object to the frame below. I ask the same question there. And below that.

I am not searching for the cause. I am looking for somebody willing to take responsibility. If nobody is, I print the travel notes and stop.

Why the family tree matters

Catching a kind catches everything below it in Figure 11.1. That is the entire mechanism behind except ShopError catching both UnknownItem and NotEnoughMoney — and it is ordinary class machinery from Chapter 10, not an exception feature.

It also explains Break 1 exactly. KeyboardInterrupt was deliberately placed outside Exception so that a program catching everything reasonable does not accidentally catch your attempt to stop it. A bare except: ignores the family tree altogether and catches from the very top.

What finally guarantees

Volume III is where finally stops being a curiosity. Once your program is holding a file open or a connection to another machine, letting go of it on every path is not tidiness — it is the difference between a program that runs for a month and one that runs out of handles by Tuesday.

What it costs

Layer 5 · CPU · try is free until it fires

In current Python, entering a try block executes no instructions at all. The compiler writes a separate table alongside the tape recording which stretches of instructions are covered by which handler. While nothing goes wrong, that table is never consulted and the code runs exactly as if the try were not there.

Raising, by contrast, is expensive: build an object, capture the travel notes, then walk down the frames consulting the table at each one. Hundreds of times the cost of an if.

That asymmetry is the whole justification for Python's culture. Guarding every risky line with a check makes the common case slower, permanently, to avoid a rare case. Wrapping it in try makes the common case free and the rare case expensive — which is the right trade whenever the rare case really is rare.

The cultural rule this produces

Try it and deal with the failure, rather than checking first.

Checking first has a second flaw beyond speed. Between your check and your action, the world can change — a file that existed a moment ago may be gone. The check does not prevent the failure; it only makes you think you have.

What Python actually does.

Your table is correct and Python's is faster, for three reasons worth knowing.

1 · The probe sequence is scrambled

Stepping to the very next slot has an unpleasant property: keys pile up into runs, and a long run makes the next collision worse, which lengthens the run. Python instead jumps around the table in a sequence derived from the whole hash, not just the part the remainder kept — so a collision at slot 6 does not push you into slot 7's business.

2 · Two arrays, not one

3 · The hash is stored alongside the key

Look at the dense array: each entry keeps the full hash. On a collision, Python compares those numbers first — a single integer comparison — and only compares the actual keys if the hashes match. Comparing two long strings is expensive; comparing two integers is one instruction. Most collisions are dismissed without ever touching the keys.

Become the machine

I have been asked for d["kiwi"]. I hash the string — walking its characters, mixing in the session secret. I keep the whole result and also take its remainder to get an index. I read one small number from the index array. It says entry 2.

I jump into the dense array at entry 2 and read the stored hash. Not equal to mine — dismissed in one instruction, without looking at the key at all. So I compute the next position in my scrambled sequence and try again. This time the stored hash matches, so now — and only now — do I compare the actual strings, character by character, to be certain.

Reflection

Every measurement in this chapter said the same thing: one unpredictable memory access dominates everything else. Hashing is arithmetic and arithmetic is nearly free. The cost is the jump.

So a structure that never jumps — one where the next thing you need is always the next thing in memory — might beat a cleverer one even while doing far more work. Chapter 3 measures that directly, and the results are larger than you will expect.

The central idea of Chapter 3

You do not pay per number. You pay per cache line.

The second mechanism.

The collector's job is to find objects that are unreachable despite having non-zero counts. It does that by walking the sixteen bytes Chapter 6 could not explain.

Why it does not run constantly

Walking every container in a large program is expensive. Doing it often would be intolerable, so the collector exploits an observation that has held on every system anyone has measured:

Where the freed memory goes

Become the machine

A frame has just been destroyed. For every slot in it, I take the address, follow it to the header, and subtract one from the count.

Most are still above zero and I move on. One reaches zero — so I run its cleanup, then walk everything it pointed at and subtract one from each of those, which may cascade further. Then I hand its memory back to the pool it came from.

Meanwhile a separate tally has been rising since the last sweep. It has just passed 700, so before running your next instruction I walk generation zero, subtract the references those objects hold in one another, and free whatever now looks unreachable. You did not ask for any of this and it happened between two of your bytecodes.

Layer 5 · CPU · what memory management costs

Reference counting is a small, constant tax paid everywhere. Every binding, every argument passed, every frame destroyed adjusts a number — and each adjustment writes to the object's header, which pulls a cache line in even if you only wanted to read the object.

The collector is the opposite: nothing most of the time, then a pause proportional to the number of tracked objects. For programs holding millions of long-lived containers those pauses are measurable, which is why gc.freeze() exists to move known-permanent data out of the way.

The trade is deliberate. Counting gives predictable, immediate cleanup at a constant cost. The collector catches what counting structurally cannot. Neither alone is sufficient.

return hands back a value and throws the frame away. yield hands back a value and keeps it — every local name, and a note of which instruction to resume at. The generator object owns that frame, so it stays alive as long as the generator does.

Beat 5

Break

Five failures.

Break 1 — the sequence that was already used

A generator is one-shot. Its frame has run to the end and been discarded; there is nothing to resume. A list can be walked a hundred times because the items are still there; a generator has no items, only a position — and the position is at the end.

This bites hardest in a pipeline. Consume it twice and the second consumer gets nothing, silently.

Break 2 — the generator that never ran

You called it and nothing happened, because calling a generator function does not run the body. If a function's purpose is its effects, it must not be a generator — or the caller must actually consume it.

Break 3 — asking a question it cannot answer

Chapter 7's Figure 19.3 explains this precisely: a generator fills in __iter__ and __next__, and no other rows. It cannot report a length because it does not know one, and cannot be indexed because it has no stored items. Those refusals are honest.

Break 4 — the loop that read the file twice

Break 1, wearing work clothes. If you genuinely need two passes you must either re-open the source or accept holding the data — and choosing between those is the engineering decision. Laziness is not free; it costs you the ability to look twice.

Break 5 — the infinite loop you asked for

An endless generator is perfectly safe until something asks for all of it. list, sum, sorted, max and in all do. Always put a limit between an infinite source and anything greedy.

Beat 6

Descend

Why laziness costs something.

Layer 5 · CPU · what resuming costs

Every next() puts a frame back on the stack, restores the instruction position, runs to the next yield, and suspends again. That is far more than reading the next slot of a row.

So a generator pipeline over a million small items can be measurably slower than building lists — while using a millionth of the memory. And it is much faster the moment the data does not fit, because the alternative is not a slow program but no program.

The honest rule: lazy when the data is large or endless or arriving; eager when it is small and you will look twice.

Become the machine

Somebody has called next() on a generator. I take the frame it has been holding, push it back onto the stack, and set the read-head to the instruction recorded inside it. Every local name is exactly as it was left.

I run forwards. I reach a yield. I take the value, write down the next instruction position in the frame, lift the frame off the stack, and hand it back to the generator object to hold. I have not returned. I have paused.

If instead I run off the end of the body, I destroy the frame properly, set gi_frame to nothing, and raise StopIteration. From then on there is nothing to resume — which is Break 1, exactly.

Layer 7 · Input / output · why this matters most at the edge

for line in f in Beat 3 never loads the file, and now you can see the whole chain: the file object is an iterator, the kernel hands over a block at a time, and Python yields lines out of it.

The same shape works for data arriving over a network, where the items do not exist yet when the loop starts. A list cannot represent that at all. Volume III is built on this — and when you meet async, it will be a generator that pauses for a different reason.

Some shapes have no fixed depth, and no number of nested loops will do. The answer is a function that hands the problem to a smaller copy of itself — and one famous example of it would take longer than the age of the universe.

Break

Five failures.

Break 1 — no way out

Volume I showed you this and could not explain the number. Break 2 — the same work, over and over

Adding five to n multiplies the time by about eleven. That is not a curve from Figure 13.2 — it is worse than all of them. fib(80) would take longer than the age of the universe.

Break 3 — the deep list

Your perfectly good walk from Beat 3 fails on structures nested more than about a thousand deep. Data from the outside world can be shaped however it likes — including deliberately, by somebody who wants your program to stop.

Break 4 — the structure that contains itself

The recursive step never gets smaller, because the structure never ends. The fix is the notebook from Chapter 7's deepcopy: keep a set of the id()s you have already visited and refuse to descend twice.

Break 5 — the accumulator that persisted

A changeable default in a recursive function is the sticky default at its most confusing, because every level of recursion shares it and so does every separate top-level call. Use None, or better, make the function a generator and let the caller collect.

Beat 6

Descend

Why the limit exists, and how to escape it.

The same shape, without the frames

Any recursion can be rewritten as a loop with a list you manage yourself. The list is the stack — you are simply doing by hand what the interpreter was doing for you.

Become the machine

I have reached walk(child, …) inside walk. I build a frame exactly as for any other call — this one is not special to me. I copy the argument addresses in, note where to come back to, and start the body.

It calls walk again. Another frame. And again. My stack is now four deep and every one of those frames is holding a half-finished for loop, each with its own position in its own dictionary.

I do not know these are the same function. There is no such concept. There are only frames, and I destroy each one as it finishes, in the reverse order I built them.

Layer 5 · CPU · what recursion costs

A frame per call — several hundred machine instructions each, plus the memory. A loop reuses one frame and pays nothing per turn.

There is also a cache cost. A loop over a row walks memory forwards, which Chapter 3 showed is ideal. Recursion over a tree follows addresses to nodes scattered across the heap, which is Figure 15.3's unpredictable pattern — the processor cannot fetch ahead.

So recursion is not free, and it is still usually right for genuinely nested shapes. Use it where the structure is nested; use a loop where the structure is a row. Reach for an explicit stack only when depth or a hostile input forces you.

Why Python will not help you here

Some languages spot that a recursive call is the very last thing a function does and quietly reuse the frame, making such recursion free and unlimited. Python deliberately does not.

The reason is Figure 11.2: reusing frames would destroy the traceback. Python's designers judged that seeing the whole chain of calls when something goes wrong is worth more than unlimited recursion depth. Whether that was right is a genuine argument — but now you know it was a choice, not an oversight.

Five ways the instrument misleads you.

Break 1 — the profiler changed the answer

cProfile records every single call, which costs time per call. Code made of millions of tiny calls is punished far more than code made of a few big ones — so the profile can rank things in the wrong order.

Use it to find where, then use timeit on that spot to find out how much. Or use a sampling profiler, which peeks at the stack a few hundred times a second and barely disturbs anything.

Break 2 — optimising the part you understand

People optimise the code they wrote most recently, or the code they find most interesting. Neither correlates with the shaded strip in Figure 22.2. The instrument exists precisely to overrule that instinct.

Break 3 — the micro-optimisation

One is measurably faster. It will improve your program by nothing at all, because it is executed a hundred times, not ten million. A real measurement of an irrelevant thing is still irrelevant.

Break 4 — the fix that made it slower

Chapter 3's Break 4. At twenty items the list wins, and you have added a structure, a conversion and some confusion in exchange for a loss. Always measure after, not only before. An optimisation you did not verify is a guess wearing a lab coat.

Break 5 — it was never your code

Thirty-eight seconds waiting for another computer. Every idea in this volume is worth nothing here — the shape is fine, the cache is irrelevant, and the fastest possible Python would save you 0.01%. The problem is somewhere Volume III begins.

Descend

Where a Python second actually goes.

Become the machine

I have been asked to profile. Before every call I note the time and push an entry; after every return I note the time again and add the difference to that function's total. I do this for every call in your program, including the ones inside libraries.

So a function called ten million times gets ten million pairs of clock readings. My measuring is now a substantial part of what is being measured — which is Break 1, and it is not a defect. It is the price of knowing exactly which function, rather than roughly where.

The honest question, before any of this

Does it need to be faster? A report that runs nightly and takes fifteen seconds is finished. Optimising it costs your time, adds structures somebody must understand, and risks a bug in code that currently works.

Speed matters when a person is waiting, when the cost is real money, or when the shape means it will stop working entirely as the data grows. Otherwise the correct optimisation is usually none — and choosing that deliberately, rather than by neglect, is an engineering decision like any other.

Every measurement in ten chapters was taken on one machine, running one process, with nothing else competing for the cache, the memory or the processor. Your stride experiment in Chapter 3 assumed the cache was yours. Chapter 10's profile assumed the clock was steady.

None of Volume II is wrong. All of it was measured in a quiet room.

You can look at a program and say what it will cost — and prove it.
